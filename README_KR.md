# RKotlin

> **저는 코틀린의 그 모호함이 싫습니다.**

RKotlin은 Kotlin에서 강하게 영향을 받은 실험적 정적 타입 객체지향 언어입니다.

대충 한 줄로 요약하면 이렇습니다.

> **Kotlin 같은데 C로 컴파일되고, 덜 모호하고, 포인터가 있습니다.**

RKotlin은 Kotlin의 좋은 점—읽기 쉬운 문법, 강한 타입 시스템, 객체지향적인 설계, 적은 문법적 소음—은 최대한 가져오면서, 코드의 실제 동작은 좀 더 명확하고 예측 가능하게 만들고자 합니다.

Kotlin은 아닙니다.

Kotlin 컴파일러도 아닙니다.

기존 Kotlin 코드를 그대로 받아주는 언어도 아닙니다.

RKotlin은 RKotlin입니다.

그리고...

RKotlin 컴파일러는 지금 Kotlin으로 만들어지고 있습니다.

상황의 아이러니는 저도 알고 있습니다. 뭐요.' 왜. 난 코틀린밖에 못한단말야.

## RKotlin이 뭔데요?

RKotlin은 Kotlin의 문법과 설계 철학에서 많은 영향을 받은 네이티브 프로그래밍 언어입니다.

대략 이런 조합을 목표로 합니다.

```text
Kotlin스러운 문법
        +
명시적인 의미
        +
네이티브 컴파일
        +
저수준 제어
```

조금 덜 점잖게 설명하면:

> Kotlin이 갑자기 포인터를 쥐여주고, 뒤에서 몰래 뭘 하지 않기 시작하면 어떨까?

대충 그게 RKotlin입니다.

RKotlin은 객체지향 언어입니다.

RKotlin은 C로 컴파일됩니다.

RKotlin은 실제 포인터를 지원할 예정입니다.

네, 이 셋은 동시에 존재할 수 있습니다.

아마도요.

# 왜 이름이 RKotlin인가요?

이름은 **RPython**에서 따왔습니다.

RPython은 Python과 비슷한 문법을 사용하지만, 정적 분석과 네이티브 컴파일이 가능하도록 Python의 일부 동적 기능을 제한한 언어입니다.

RKotlin도 비슷한 발상에서 출발했습니다.

```text
Python  → RPython
Kotlin  → RKotlin
```

다만 RKotlin은 단순히 “Kotlin의 제한된 부분집합”을 만드는 것이 목표는 아닙니다.

Kotlin의 문법과 객체지향적인 사용감을 바탕으로 하면서도, 더 명확한 타입과 의미론, C 컴파일, 저수준 기능, 그리고 포인터 같은 기능을 적극적으로 추가하는 독립적인 언어를 목표로 합니다.

즉 RKotlin의 `R`은 굳이 하나의 단어로 정확히 풀 필요는 없습니다.

원한다면:

```text
Restricted Kotlin
Reduced Kotlin
Resolved Kotlin
Really Kotlin?
```

정도로 읽어도 됩니다.

마지막 것은 공식적인 의미가 아닐겁니다.

아마도요.

중요한 건 이름의 계보입니다.

> **RPython이 Python에서 출발했듯이, RKotlin은 Kotlin에서 출발합니다.**

하지만 출발지가 같다고 목적지까지 같을 필요는 없습니다.

RKotlin은 Kotlin을 그대로 옮기는 프로젝트가 아니라, Kotlin을 출발점으로 삼아 다른 방향으로 자라는 언어입니다.

# 설계 철학

RKotlin이 가장 중요하게 생각하는 원칙은 하나입니다.

> **중요한 동작은 코드에 드러나야 한다.**

추상화는 좋습니다.

편의 기능도 좋습니다.

타입 추론도 좋습니다.

하지만 코드가 실제로 무엇을 하는지 흐려지기 시작하면 이야기가 달라집니다.

RKotlin이 되도록 줄이고 싶은 질문들은 이런 것들입니다.

```text
이 함수 호출은 정확히 어느 함수를 부르는 거지?

이 값은 암시적으로 변환된 건가?

왜 boxing이 일어났지?

여기서 메모리 할당이 일어나나?

이 이름은 실제로 어디를 가리키는 거지?

컴파일러는 왜 이걸 이렇게 해석한 거지?

나는 왜 새벽 2시 47분에 생성된 코드를 읽고 있지?
```

음... 아주 안타깝게도 마지막 문제까지 해결해주지는 못합니다. 슈퍼-갓- gpt-6 Astra도 해결 못하는거에요.

그러나 나머지는 협상의 여지가 있습니다.

RKotlin의 목표는 추상화를 없애는 것이 아닙니다.

그렇게 하면 그냥 문장부호가 예쁜 어셈블리가 되죠.

목표는 **의미적 모호성**을 줄이는 것입니다.

의미 분석이 끝난 시점에는 컴파일러가 최소한 다음 정도는 확실히 알고 있어야 합니다.

* 각 식별자가 정확히 어떤 선언을 가리키는지
* 각 함수 호출이 어느 함수로 해석되는지
* 각 표현식의 타입이 무엇인지
* 각 연산자가 어떤 실제 연산을 의미하는지
* 어떤 변수가 변경 가능한지
* 어디에서 상태가 변경되는지
* 언제 형변환이 일어나는지
* 나중에는 어떤 코드가 위험한 메모리 접근을 하는지

백엔드까지 내려간 시점에는 프로그램의 의미가 이미 결정되어 있어야 합니다.

백엔드는 번역하면 됩니다.

# 현재 기능

RKotlin은 아직 실험적인 언어지만, 이미 간단한 프로그램 수준은 넘어섰습니다.

현재 구현된 주요 기능은 다음과 같습니다.

* 정적 타입 함수
* 함수 매개변수
* 명시적 반환 타입
* 지역 변수
* `val`
* `var`
* 대입
* 산술 연산
* 함수 호출
* 중첩 표현식
* 표준 입력
* 표준 출력
* `if`
* `for`
* `while`
* 객체 생성
* 객체지향 관련 기능
* 의미 분석
* 중간 표현(IR)
* C 코드 생성

예를 들면 이런 코드가 가능합니다.

```kotlin
fun add(a: Int32, b: Int32): Int32 {
    return a + b
}

fun mul(a: Int32, b: Int32): Int32 {
    return add(a * 2, b + 3)
}

fun main(): Int32 {
    var x: Int32 = 10

    x = x + 32

    println(x)

    return mul(x, x + 1)
}
```

이 코드는 인터프리터에서 실행되지 않습니다.

RKotlin 컴파일러는 소스를 파싱하고, 의미 분석을 하고, IR로 낮춘 뒤, C 코드로 변환합니다.

대략 이런 식의 C가 생성될 수 있습니다.

```c
int32_t rk_main(void) {
    int32_t l0;

    l0 = 10;

    int32_t r0 = l0;
    int32_t r1 = r0 + 32;

    l0 = r1;

    int32_t r2 = l0;
    int32_t r3 = l0;
    int32_t r4 = r3 + 1;

    int32_t r5 = rk_mul(r2, r4);

    return r5;
}
```

예쁜 C냐고요?

아니요.

예뻐야 하냐고요?

그것도 아닙니다.

C 컴파일러는 `r7`이라는 변수명을 보고 상처받지 않습니다.

아마도요.

# 변수

RKotlin은 변경 가능한 변수와 변경 불가능한 변수를 구분합니다.

```kotlin
val x: Int32 = 10
var y: Int32 = 20
```

`val`은 재대입할 수 없습니다.

```kotlin
val x: Int32 = 10

x = 20
```

이 코드는 오류입니다.(테스트 안해봄)

반대로 `var`는 변경할 수 있습니다.

```kotlin
var x: Int32 = 10

x = 20
```

이 코드는 정상입니다.

상태가 바뀐다면 코드에서도 그 사실이 보여야 합니다.

변경이 숨어 있고, 나중에 독자가 탐정놀이를 해야 하는 문법은 별로 좋아하지 않습니다.

# 대입은 표현식이 아닙니다

RKotlin에서 대입은 값을 만들어내는 표현식이 아니라, 상태를 바꾸는 문장입니다.

이건 됩니다.

```kotlin
x = 42
```

이건 안 됩니다.

```kotlin
foo(x = 42)
```

이것도 안 됩니다.

```kotlin
a = b = c = 42
```

C가 오랫동안 즐겨왔던 문법입니다.

RKotlin은 정중히 사양합니다.

덕분에 이런 류의 실수도 피할 수 있습니다.

```c
if (x = 3)
```

총알 하나는 미리 제거했습니다.

아직 총은 많네요.

# 제어문

RKotlin은 일반적인 명령형 제어 흐름을 지원합니다.

## `if`

```kotlin
fun main(): Int32 {
    val x: Int32 = input()

    if (x > 10) {
        println(x)
    }

    return 0
}
```

## `while`

```kotlin
fun main(): Int32 {
    var x: Int32 = 10

    while (x > 0) {
        println(x)
        x = x - 1
    }

    return 0
}
```

## `for`

```kotlin
fun main(): Int32 {
    for (i: Int32 in 0..10) {
        println(i)
    }

    return 0
}
```

다만 언어가 아직 어리기 때문에 세부 문법이나 의미는 바뀔 수 있습니다.

몇 시간 전에 작성한 코드가 깨지는 일도 당분간은 있을 수 있습니다.

안타깝지만... 저도 나쁜 코드가 제 언어에 들어오는걸 용서할순 없어요!

```kotlin
fun main(): Int32 {
```

# 객체지향

RKotlin은 객체지향 언어입니다.

객체 생성은 이미 지원합니다.

개념적으로 이런 코드를 목표로 하고 있습니다.

```kotlin
class Point(
    var x: Int32,
    var y: Int32
)

fun main(): Int32 {
    val point: Point = Point(10, 20)

    println(point.x)

    return 0
}
```

장기적으로는 다음과 같은 요소들을 다룰 예정입니다.

* 클래스
* 필드
* 메서드
* 생성자
* 캡슐화
* 합성
* 인터페이스 또는 유사한 추상화

객체 모델은 아직 바뀌는 중입니다.

앞으로도 몇 번 더 바뀔 가능성이 큽니다.

컴파일러 개발은 꽤 자주 “이거 완벽하다”라고 말한 다음 이틀 뒤에 지우는 작업이거든요.
어떻게 알았냐고요? 저도 알고싶지 않았어요.

# 포인터

포인터는 RKotlin의 핵심 목표 중 하나입니다.

“내부적으로는 주소지만 굳이 포인터라고 부르진 않는 것”이 아닙니다.

진짜 포인터입니다.

대략 이런 방향을 생각하고 있습니다.

```kotlin
var ptr: Pointer<Int32>
```

그리고 명시적인 읽기/쓰기 연산:

```kotlin
val value: Int32 = ptr.read()

ptr.write(42)
```

저수준 메모리 접근은 일반 코드와 확실히 구분되어야 합니다.

그래서 장기적으로는 다음과 같은 `unsafe` 경계를 둘 가능성이 큽니다.

```kotlin
unsafe {
    ptr.write(42)
}
```

정확한 문법은 아직 확정하지 않았습니다.

다만 원칙은 있죠.

> 메모리를 현대미술 작품으로 만들 수 있는 코드라면, 소스에서도 티가 나야 합니다.

# 네이티브 컴파일

RKotlin은 현재 C를 중간 백엔드로 사용합니다.

컴파일 흐름은 대략 다음과 같습니다.

```text
RKotlin 소스
     │
     ▼
   Lexer
     │
     ▼
   Token
     │
     ▼
   Parser
     │
     ▼
    AST
     │
     ▼
 의미 분석
     │
     ▼
 Bound 표현
     │
     ▼
     IR
     │
     ▼
  C Backend
     │
     ▼
   C 소스
     │
     ▼
GCC / Clang / MinGW
     │
     ▼
네이티브 실행 파일
```

중요한 점은 C가 RKotlin의 의미론이 아니라는 것입니다.

C는 구현을 위한 출력 형식입니다.

RKotlin 프로그램이 무엇을 의미하는지는 그 전에 이미 결정됩니다.

C 백엔드는 최대한 멍청한 편이 좋습니다. 마치 저처럼요.

좋은 백엔드는 IR을 보고 이렇게 말해야 합니다.

> 네. 이 명령은 이렇게 출력하면 되겠네요.

이렇게 말하면 안 됩니다.

> 흥미롭군요. 작성자가 뭘 의도한 걸까요?

---

## 네이티브 C 컴파일러

`-p` 또는 `-r` 옵션을 사용하면 운영체제에 맞는 C 컴파일러를 선택합니다.

* Windows: 프로젝트의 MinGW-w64를 사용하고 없으면 자동 설치합니다.
* macOS: `clang`을 우선 사용하며, 없으면 Homebrew로 LLVM을 설치합니다.
* Linux: `clang`, `gcc`, `cc` 순서로 찾고, 없으면 `apt`, `dnf`, `pacman` 중
  사용 가능한 패키지 매니저로 개발 도구를 설치합니다.

Linux와 macOS에서는 설치 과정에서 `sudo` 또는 Homebrew 권한이 필요할 수 있습니다.

# 중간 표현(IR)

RKotlin은 복잡한 표현식을 명시적인 임시 값들로 낮춥니다.

예를 들어:

```kotlin
return add(
    mul(a, b),
    add(b, c)
)
```

내부적으로는 대략 다음과 비슷한 구조가 됩니다.

```text
r0 = call mul(a, b)
r1 = call add(b, c)
r2 = call add(r0, r1)
ret r2
```

C로는:

```c
int32_t r0 = rk_mul(a, b);
int32_t r1 = rk_add(b, c);
int32_t r2 = rk_add(r0, r1);

return r2;
```

지역 변수와 임시 값도 분리합니다.

개념적으로:

```text
l0, l1, l2 ... = 지역 변수

r0, r1, r2 ... = 계산용 임시 값
```

예를 들어:

```kotlin
var x: Int32 = 10

x = x + 32
```

은 대략:

```text
local l0: i32

store l0, 10

r0 = load l0
r1 = add.i32 r0, 32

store l0, r1
```

처럼 내려갈 수 있습니다.

장황합니다.

의도된 장황함입니다.

IR은 영리한 것보다 명확한 편이 좋습니다.

최적화는 다른 문제입니다.

괴물은 한 번에 하나씩 잡읍시다.

# 왜 C로 컴파일하나요?

C는 거의 어디에나 있기 때문입니다.

그리고 이미 성숙한 C 컴파일러들이 다음 문제를 해결해놓았습니다.

* 명령어 선택
* 레지스터 할당
* 호출 규약
* 최적화
* 오브젝트 파일
* 플랫폼 차이
* x86-64
* ARM
* AArch64
* Windows
* Linux
* macOS
* 그리고 수십 년간 쌓인 온갖 업보

RKotlin은 굳이 그 모든 업보를 처음부터 다시 쌓을 필요는 없습니다.

C를 백엔드로 사용하면 프로젝트는 다음에 집중할 수 있습니다.

```text
문법
타입
의미론
객체
메모리 모델
언어 설계
```

언젠가는 다른 백엔드를 만들 수도 있습니다.

```text
RKotlin → C
RKotlin → LLVM IR
RKotlin → x86-64
RKotlin → AArch64
RKotlin → WebAssembly
```

하지만 지금은:

> C는 됩니다.

놀랍도록 강력한 장점입니다.

# 왜 C++이 아닌가요?

그러면 C++을 쓰게 되니까요.

이게 가장 짧은 답입니다.

조금 더 길게 말하면 C++은 RKotlin과 다른 문제를 해결하는 언어입니다.

C++은 굉장히 강력합니다.

그리고 수십 년 동안 호환성을 유지하면서 기능을 쌓아왔습니다.

그 결과 이런 것들이 있습니다.

* 암시적 변환
* 복잡한 오버로드 결정
* 템플릿
* 참조
* 이동 의미론
* 여러 종류의 초기화 문법
* 연산자 오버로딩
* 상속
* 다중 상속
* 값 범주
* 정의되지 않은 동작
* 구현 정의 동작
* 문장부호 노동조합이 필요할 정도의 문법

RKotlin은 C++보다 더 C++ 같은 언어가 되려는 것이 아닙니다.

> 수십 년간의 C와 C++ 호환성을 유지하면서 얼마나 많은 기능을 제공할 수 있을까?

RKotlin은 이런 질문을 합니다.

> 그냥 새로 만들고, 필요 없는 기능에는 "아니오"라고 말하면 안 되나?

둘 다 좋은 질문입니다.

결과가 다를 뿐.

# 왜 Rust가 아닌가요?

Rust는 훌륭한 언어입니다.

RKotlin은 “Rust 별로고 내 언어 최고” 프로젝트가 아닙니다.

Rust는 이미 다음을 잘 해결하고 있습니다.

* GC 없는 메모리 안전성
* 강력한 소유권 시스템
* 정교한 타입 시스템
* 좋은 도구
* 성숙한 시스템 프로그래밍 생태계

RKotlin은 목표가 다릅니다.

문법과 전체적인 사용감에서 Kotlin의 영향을 훨씬 강하게 받습니다.

Rust의 소유권 모델을 복제하는 것도 목표가 아닙니다.

애초에 Kotlin으로 자작 컴파일러를 만들어 Rust를 정면승부로 이기겠다는 건 꽤 바보같은 취미죠.

# 왜 Kotlin/Native가 아닌가요?

RKotlin은 Kotlin이 아니기 때문입니다.

Kotlin/Native는 Kotlin이라는 언어 자체의 의미와 생태계를 유지하면서 네이티브 타깃을 지원합니다.

RKotlin은 다른 선택을 할 자유가 있습니다.

예를 들어:

* Kotlin 기능을 일부 제거할 수 있고
* 의미를 바꿀 수 있고
* 타입을 더 명시적으로 요구할 수 있고
* 포인터를 직접 노출할 수 있고
* 객체 모델을 다르게 설계할 수 있고
* 런타임을 더 작게 만들 수 있고
* 암시적인 동작을 거부할 수 있습니다

Kotlin과의 소스 호환성은 핵심 목표가 아닙니다.

대신 언어 설계의 자유를 선택합니다.

필요하면 좀 많이 과격하게요.

---

# 목표가 아닌 것

RKotlin은 현재 다음을 목표로 하지 않습니다.

## Kotlin의 대체품

기존 Kotlin 프로젝트가 수정 없이 그대로 컴파일될 거라고 기대하지 마세요.

만약 된다면 대단하거나 수상한 일입니다.

## JVM 생태계 호환

RKotlin은 네이티브 언어입니다.

기존 JVM 라이브러리를 그대로 사용하는 것은 목표가 아닙니다.

## Kotlin 기능 전부 복제하기

Kotlin에 있는 기능이라고 해서 자동으로 RKotlin에도 들어오지는 않습니다.

“코틀린에 있으니까”는 충분한 설계 근거가 아닙니다.

## 마법 같은 언어

중요한 런타임 동작이 innocuous한 문법 뒤에 숨어 있는 것을 피하고자 합니다.

편의성은 좋습니다.

강령술은 아닙니다.

## Kotlin 문법을 입힌 C

RKotlin은 단순히:

```text
C
+
Kotlin 비슷한 문장부호
```

가 아닙니다.

타입 시스템, 객체 모델, 의미론, 컴파일러 구조 자체를 별도로 설계합니다.

## 무조건 안전한 언어

RKotlin은 포인터와 직접 메모리 접근을 허용할 예정입니다.

위험한 기능은 존재할 수밖에 없습니다.

목표는 위험을 없애는 것이 아니라 **드러내는 것**입니다.

## 안정된 언어

아직 아닙니다.

전혀 아닙니다.

현재 문법을 몸에 문신하지 마세요.

## 함수

```kotlin
fun add(a: Int32, b: Int32): Int32 {

}
```

## 중첩 호출

```kotlin
fun mul(a: Int32, b: Int32): Int32 {
    return add(a * 2, b + 3)
}

fun f(a: Int32, b: Int32, c: Int32): Int32 {
    return add(
        mul(a, b),
        add(b, c)
    )
```

```kotlin
fun main(): Int32 {
```

```kotlin
fun main(): Int32 {

    return 0
}
```

```kotlin
fun main(): Int32 {

    }

}
```

```kotlin
fun main(): Int32 {
```

```kotlin
fun main(): Int32 {
```

# 현재 상태

RKotlin은 현재 다음 흐름을 실제로 처리할 수 있습니다.

```text
함수
  ↓
표현식
  ↓
변수
  ↓
상태 변경
  ↓
함수 호출
  ↓
입출력
  ↓
분기
  ↓
반복
  ↓
객체
  ↓
C 코드
  ↓
네이티브 실행 파일
```

이제 프로젝트는 이미:

> 이 언어가 존재할 수 있을까?

라는 단계는 지나왔습니다.

요즘 질문은 오히려 이쪽입니다.

> 나는 대체 언어를 어디까지 만들 생각이지?

아무래도 꽤 멀리 갈 것 같습니다.

현재 컴파일러의 우선순위는:

```text
정확한 의미
   >
명확한 IR
   >
예쁜 생성 C 코드
```

입니다.

생성되는 C는 임시 변수가 많이 들어갈 수 있습니다.

```c
int32_t r0 = l0;
int32_t r1 = r0 + 32;
l0 = r1;

int32_t r2 = l0;
int32_t r3 = l0;
int32_t r4 = r3 + 1;
```

상관없습니다.

요즘 C 컴파일러는 이런 걸 정리하는 데 매우 능숙합니다.

현재 최적화 전략은 다음과 같습니다.

> 1단계: 정확한 코드를 만든다.
> 2단계: Clang에게 던진다.

고급 최적화는 일단 전 못합니다. gcc 도와줘!

# 컴파일러 구조

RKotlin 컴파일러는 현재 Kotlin으로 작성되어 있습니다.

전체 구조는 전통적인 다단계 컴파일러 구조에 가깝습니다.

대략:

```text
source/
    SourceFile
    SourceSpan

lexer/
    Token
    TokenType
    Lexer

ast/
    declaration
    statement
    expression

parser/
    Parser

semantic/
    type
    symbol
    scope
    semantic analysis
    bound node

ir/
    value
    instruction
    function
    module

backend/
    C backend
```

각 단계는 역할을 분리합니다.

Lexer는 타입 검사를 하지 않습니다.

Parser는 `val`에 재대입해도 되는지 판단하지 않습니다.

Semantic Analyzer는 C 코드를 생성하지 않습니다.

C Backend는 이름 해석을 하지 않습니다.

이 구분은 꽤 중요합니다.

안 그러면 어느 날 컴파일러 전체가 8,000줄짜리:

```text
Compiler.kt
```

한 파일로 자라납니다.

그러면 뭐... 말 안해도 알죠?

# 오류 처리

RKotlin은 오류가 실제로 속한 단계에서 오류를 처리하려고 합니다.

예를 들어:

```kotlin
val x: Int32 = 10

x = 20
```

이 코드는 문법적으로는 올바릅니다.

따라서 Parser는 받아들입니다.

하지만 의미상 `x`는 변경 불가능하므로 의미 분석 단계에서 오류가 납니다.

마찬가지로:

```kotlin
var x: Int32 = 10

x = somethingCompletelyWrong
```

도 파싱 자체는 가능하지만 이름 해석이나 타입 검사에서 실패할 수 있습니다.

“문법적으로 맞는 코드”와 “실제로 유효한 프로그램”은 같은 개념이 아닙니다.

이걸 분리해두면 컴파일러 구조가 훨씬 덜 미쳐갑니다.

# 그런데 왜 컴파일러는 Kotlin으로 만들었나요?

Kotlin이 편하니까요.

네, 철학적으로 약간 문제가 있습니다.

RKotlin은 Kotlin의 몇몇 부분이 마음에 들지 않아서 만든 언어입니다.

그런데 RKotlin 컴파일러는 Kotlin으로 작성되어 있습니다.

현재 상황을 요약하면:

```text
"나는 Kotlin이 마음에 안 들어."

          ↓

Kotlin 수천 줄 작성

          ↓

RKotlin 탄생
```

부트스트래핑입니다.

아마도요.

Kotlin은 첫 번째 컴파일러를 빠르게 만들기에 좋은 언어입니다.

RKotlin이 충분히 성장하고 안정되면 그때 자기 자신으로 컴파일러를 만들 수 있습니다.

그전까지 Kotlin은 사다리입니다.

RKotlin은 나중에 그 사다리를 걷어찰 예정일 뿐입니다.

# 설계 우선순위

설계 목표가 충돌한다면 RKotlin은 대체로 다음을 우선합니다.

```text
마법보다 예측 가능성

숨은 동작보다 명시성

영리한 문법보다 분명한 의미

예쁜 C보다 정확한 코드 생성

성급한 추상화보다 단순한 컴파일러 구조

순수함보다 유용한 저수준 접근
```

그렇다고 일부러 장황한 언어를 만들겠다는 뜻은 아닙니다.

명시적이라는 것과 불편하다는 것은 같은 말이 아닙니다.

RKotlin이 찾고 싶은 지점은:

> 컴파일러가 개발자를 돕되, 몰래 공동 저자가 되지는 않는 지점

입니다.

# AI 사용에 대하여

이 프로젝트의 개발 과정에서 AI 도구를 사용했습니다.

AI는 주로 다음과 같은 작업을 보조하는 데 사용되었습니다.

* 문서 초안 작성 및 문장 다듬기
* 코드 아이디어와 구조 검토
* 반복적인 코드 작성 보조
* 테스트 케이스 및 예제 생성
* 컴파일러 설계에 대한 브레인스토밍
* 이 문서를 쓰는 것

다만 AI가 이 프로젝트를 자동으로 설계하거나 완성한 것은 아닙니다.

RKotlin의 언어 설계, 구현 방향, 기능 선택, 컴파일러 구조에 대한 최종 판단과 책임은 프로젝트 작성자에게 있습니다. AI가 생성하거나 제안한 내용 역시 그대로 신뢰하지 않고 필요에 따라 검토, 수정, 재작성합니다.

또한 AI가 작성에 참여했다는 사실은 코드의 정확성이나 안전성을 보장하지 않습니다.

이 프로젝트는 아직 실험 단계이며, 버그가 있을 수 있습니다.

매우 있을 수 있습니다.
