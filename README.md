# RKotlin

> **I don't like Kotlin's ambiguity.**

RKotlin is an experimental, statically typed, object-oriented programming language inspired by Kotlin.

The idea is simple:

> **Kotlin, but compiled to C. Less ambiguity. With pointers.**

RKotlin tries to preserve the parts of Kotlin that make it pleasant to write—clean syntax, strong typing, object-oriented design, and relatively low syntactic noise—while making behavior more explicit and predictable.

It is not Kotlin.

It is not a Kotlin compiler.

It is not intended to compile arbitrary Kotlin code.

RKotlin is its own language.

And yes, the RKotlin compiler is currently written in Kotlin.

I am aware of the situation.

---

## What is RKotlin?

RKotlin is a native programming language heavily inspired by Kotlin.

Its basic design can be summarized as:

```text
Kotlin-like syntax
        +
explicit semantics
        +
native compilation
        +
low-level access
```

Or, in less respectable terminology:

> What if Kotlin gave me a pointer and stopped making mysterious decisions behind my back?

RKotlin is object-oriented.

RKotlin compiles to C.

RKotlin is intended to support real pointers.

These are not mutually exclusive concepts.

I checked.

---

# Why is it called RKotlin?

The name is inspired by **RPython**.

RPython uses Python-like syntax while restricting some of Python's dynamic behavior so that programs can be analyzed and compiled more predictably.

RKotlin started from a similar idea.

```text
Python  → RPython
Kotlin  → RKotlin
```

That said, RKotlin is not intended to be merely a restricted subset of Kotlin.

It uses Kotlin as a starting point, but it is free to make different choices: stricter semantics, more explicit types, native C compilation, low-level features, and eventually real pointers.

So the `R` does not necessarily have to stand for one specific word.

You may read it as:

```text
Restricted Kotlin
Reduced Kotlin
Resolved Kotlin
Really Kotlin?
```

The last one is not the official meaning.

Probably.

What matters more is the lineage:

> **Just as RPython grew out of Python, RKotlin grows out of Kotlin.**

But sharing a starting point does not mean sharing a destination.

RKotlin is not trying to preserve Kotlin exactly.

It is trying to take some of Kotlin's ideas and grow them in a different direction.

---

# Philosophy

RKotlin has one central design principle:

> **Important behavior should be visible.**

Abstraction is useful.

Convenience is useful.

Inference is useful.

But when those features begin to obscure what a program actually means, things get less pleasant.

Questions RKotlin would prefer to minimize include:

```text
Which overload did this call?

Was this converted implicitly?

Why was this boxed?

Did this allocate?

Which variable does this name actually refer to?

Why is the compiler doing that?

Why am I reading generated bytecode at 2:47 AM?
```

RKotlin cannot solve the final problem.

The others are negotiable.

The goal is not to eliminate abstraction.

That would merely produce assembly with better punctuation.

The goal is to reduce **semantic ambiguity**.

After semantic analysis, the compiler should know exactly:

* which declaration every identifier refers to,
* which function every call resolves to,
* what type every expression has,
* what operation every operator represents,
* whether a variable is mutable,
* when state changes occur,
* when a conversion happens,
* and eventually when unsafe memory access happens.

By the time code reaches the backend, its meaning should already be decided.

The backend should translate.

It should not investigate.

# Features

RKotlin is still experimental, but it can already compile non-trivial programs.

Currently implemented functionality includes:

* statically typed functions,
* function parameters,
* explicit return types,
* local variables,
* `val`,
* `var`,
* assignment,
* arithmetic expressions,
* function calls,
* nested expressions,
* standard input,
* standard output,
* `if`,
* `for`,
* `while`,
* object creation,
* object-oriented language features,
* semantic analysis,
* an intermediate representation,
* and native C code generation.

Example:

```kotlin
fun add(a: Int32, b: Int32): Int32 {
    return a + b
}

fun mul(a: Int32, b: Int32): Int32 {
    return add(a * 2, b + 3)
}

fun main(): Int32 {
    var x: Int32 = 10

    x = x + 32

    println(x)

    return mul(x, x + 1)
}
```

This code is not interpreted.

It is parsed, analyzed, lowered, translated to C, and then compiled by a native C compiler.

Something conceptually similar to:

```c
int32_t rk_main(void) {
    int32_t l0;

    l0 = 10;

    int32_t r0 = l0;
    int32_t r1 = r0 + 32;

    l0 = r1;

    int32_t r2 = l0;
    int32_t r3 = l0;
    int32_t r4 = r3 + 1;

    int32_t r5 = rk_mul(r2, r4);

    return r5;
}
```

Is this beautiful C?

No.

Does it have to be?

Also no.

The C compiler is not emotionally affected by temporary variable names.

Probably.

# Variables

RKotlin distinguishes immutable and mutable local variables.

```kotlin
val x: Int32 = 10
var y: Int32 = 20
```

`val` represents an immutable binding.

```kotlin
val x: Int32 = 10

x = 20
```

This is invalid.

`var` represents mutable state.

```kotlin
var x: Int32 = 10

x = 20
```

This is valid.

Mutation should be visible.

RKotlin does not want state changes hiding in places where the reader needs archaeology equipment.

---

# Assignment is a Statement

Assignment is treated as a state-changing statement rather than a value-producing expression.

This is valid:

```kotlin
x = 42
```

This is intentionally not:

```kotlin
foo(x = 42)
```

Neither is:

```kotlin
a = b = c = 42
```

C has enjoyed that syntax for long enough.

RKotlin respectfully declines.

This also keeps assignment semantics simple:

```text
target
=
value
```

No chaining.

No assignment expression.

No accidental condition such as:

```c
if (x = 3)
```

One less historical footgun to inherit.

# Control Flow

RKotlin supports ordinary imperative control flow.

## `if`

```kotlin
fun main(): Int32 {
    val x: Int32 = input()

    if (x > 10) {
        println(x)
    }

    return 0
}
```

## `while`

```kotlin
fun main(): Int32 {
    var x: Int32 = 10

    while (x > 0) {
        println(x)
        x = x - 1
    }

    return 0
}
```

## `for`

```kotlin
fun main(): Int32 {
    for (i: Int32 in 0..10) {
        println(i)
    }

    return 0
}
```

The exact semantics of newer features may still change while RKotlin is young.

Breaking compatibility with code written earlier the same evening is currently considered unfortunate but survivable.

# Input and Output

Basic input and output are already available.

For example:

```kotlin
fun main(): Int32 {
    println("Enter a number:")

    val x: Int32 = input()

    println(x)

    return 0
}
```

The standard library is intentionally small for now.

The immediate goal is not to reproduce an enormous ecosystem.

The immediate goal is to make the language itself coherent.

# Object-Oriented Programming

RKotlin is an object-oriented language.

Object creation is already supported.

Conceptually, code can look like:

```kotlin
class Point(
    var x: Int32,
    var y: Int32
)

fun main(): Int32 {
    val point: Point = Point(10, 20)

    println(point.x)

    return 0
}
```

RKotlin aims to support familiar object-oriented concepts such as:

* classes,
* fields,
* methods,
* encapsulation,
* constructors,
* composition,
* interfaces or similar abstractions.

The object model is still evolving.

That means it may change.

Possibly repeatedly.

Compiler development is partly the art of designing something confidently and deleting it two days later.

---

# Pointers

Pointers are one of RKotlin's core design goals.

Not:

> "references that are technically addresses internally"

Actual pointers.

Something conceptually like:

```kotlin
var ptr: Pointer<Int32>
```

with explicit operations such as:

```kotlin
val value: Int32 = ptr.read()

ptr.write(42)
```

Low-level memory operations should be clearly distinguishable from ordinary code.

RKotlin will likely introduce an explicit unsafe boundary:

```kotlin
unsafe {
    ptr.write(42)
}
```

The exact syntax is still undecided.

The principle is not.

> If an operation can turn memory into modern art, the source code should probably mention it.

# Native Compilation

RKotlin currently compiles through C.

The compiler pipeline roughly looks like this:

```text
RKotlin source
      │
      ▼
    Lexer
      │
      ▼
    Tokens
      │
      ▼
    Parser
      │
      ▼
     AST
      │
      ▼
Semantic Analysis
      │
      ▼
Bound Representation
      │
      ▼
Intermediate Representation
      │
      ▼
   C Backend
      │
      ▼
   C Source
      │
      ▼
 GCC / Clang / MinGW
      │
      ▼
Native Executable
```

C is an implementation backend.

It is not RKotlin's semantic model.

That distinction matters.

The frontend determines what the program means.

The backend translates that meaning into C.

Ideally, the C backend should be extremely boring.

A backend should be able to look at an IR instruction and say:

> Yes. I know what to emit.

Not:

> Fascinating. I wonder what the programmer intended.

# Intermediate Representation

RKotlin lowers complex expressions into explicit temporary values.

For example:

```kotlin
return add(
    mul(a, b),
    add(b, c)
)
```

may become something like:

```text
r0 = call mul(a, b)
r1 = call add(b, c)
r2 = call add(r0, r1)
ret r2
```

which can then become:

```c
int32_t r0 = rk_mul(a, b);
int32_t r1 = rk_add(b, c);
int32_t r2 = rk_add(r0, r1);

return r2;
```

Mutable locals and temporary values are intentionally separated.

Conceptually:

```text
l0, l1, l2 ... = local variables

r0, r1, r2 ... = temporary results
```

Example:

```kotlin
var x: Int32 = 10

x = x + 32
```

can lower approximately to:

```text
local l0: i32

store l0, 10

r0 = load l0
r1 = add.i32 r0, 32

store l0, r1
```

This is intentionally verbose.

Verbose intermediate code is easier to inspect and reason about.

Optimization is a separate problem.

One monster at a time.

# Why C?

Because C already exists everywhere.

More importantly, mature C compilers already handle:

* instruction selection,
* register allocation,
* calling conventions,
* optimization,
* object files,
* platform differences,
* x86-64,
* ARM,
* AArch64,
* Windows,
* Linux,
* macOS,
* and several decades of consequences.

RKotlin currently does not need to rediscover all of those consequences.

Using C allows the project to focus on:

```text
syntax
types
semantics
objects
memory model
language design
```

without simultaneously requiring a production-quality native machine-code backend.

Possible future backends could include:

```text
RKotlin → C
RKotlin → LLVM IR
RKotlin → x86-64
RKotlin → AArch64
RKotlin → WebAssembly
```

But for now:

> C works.

That is an alarmingly effective design argument.

---

# Why not C++?

Because then I would be writing C++.

That is technically the short answer.

The longer answer is that C++ solves a very different problem.

C++ is enormously powerful.

It also carries decades of compatibility requirements and accumulated features.

That includes things such as:

* implicit conversions,
* complex overload resolution,
* templates,
* references,
* move semantics,
* multiple initialization syntaxes,
* operator overloading,
* inheritance,
* multiple inheritance,
* value categories,
* undefined behavior,
* implementation-defined behavior,
* and enough punctuation to qualify as a separate writing system.

RKotlin is not trying to outperform C++ at being C++.

Its intended tradeoff is different:

```text
fewer mechanisms
+
more explicit semantics
+
Kotlin-like syntax
+
native low-level access
```

C++ asks:

> How much power can we provide while maintaining compatibility with decades of existing C and C++?

RKotlin asks:

> What if we started again and were allowed to say no?

Both are valid questions.

They simply produce very different languages.

---

# Why not Rust?

Rust is excellent.

RKotlin is not a "Rust bad, my language good" project.

Rust provides:

* memory safety without garbage collection,
* a strong ownership system,
* an advanced type system,
* excellent tooling,
* and a mature systems-programming ecosystem.

RKotlin exists because its goals are different.

It is much more heavily influenced by Kotlin's syntax and object-oriented style.

RKotlin is not attempting to reproduce Rust's ownership model or ecosystem.

Attempting to defeat Rust by writing a home-made compiler in Kotlin would also be an unusually aggressive hobby.

---

# Why not Kotlin/Native?

Because RKotlin is not intended to be Kotlin.

Kotlin/Native exists to compile Kotlin to native platforms while keeping Kotlin's language semantics and ecosystem.

RKotlin is free to make different decisions.

RKotlin may:

* remove Kotlin features,
* change semantics,
* require more explicit types,
* expose pointers directly,
* use a different object model,
* use a smaller runtime,
* reject implicit behavior,
* and introduce constructs that would not make sense in ordinary Kotlin.

Source compatibility is not a primary objective.

Freedom to break compatibility is.

Sometimes violently.

---

# Non-goals

RKotlin does **not** currently aim to be:

## A drop-in Kotlin replacement

Existing Kotlin projects are not expected to compile unchanged.

If one does, that is either impressive or deeply suspicious.

## Fully compatible with the JVM ecosystem

RKotlin is a native language.

Running arbitrary JVM libraries is not a goal.

## Kotlin with every feature preserved

Features are included because they fit RKotlin.

Not because Kotlin has them.

"Because Kotlin does it" is not a complete design argument.

## A magical language

RKotlin should avoid hiding important runtime behavior behind harmless-looking syntax.

Convenience is useful.

Necromancy is not.

## C with Kotlin syntax

RKotlin is not simply:

```text
C
+
different punctuation
```

Its semantics, type system, object model, and compiler architecture are intended to stand on their own.

## Perfectly safe at all costs

RKotlin intends to support pointers and direct memory access.

That means dangerous operations must exist.

The goal is to make them explicit and controlled.

Not to pretend they do not exist.

## Stable

Absolutely not.

Not yet.

Do not tattoo the grammar onto your body.

# Current Status

RKotlin can currently compile programs containing:

```text
functions
    ↓
expressions
    ↓
variables
    ↓
mutation
    ↓
function calls
    ↓
input/output
    ↓
branches
    ↓
loops
    ↓
objects
    ↓
C
    ↓
native executable
```

At this point, the project has moved past:

> Can this language exist?

The question is increasingly:

> How much of a language am I accidentally building?

Apparently, quite a lot.

The compiler currently prioritizes:

```text
correct semantics
    >
clear IR
    >
pretty generated C
```

Generated C may contain many temporary values:

```c
int32_t r0 = l0;
int32_t r1 = r0 + 32;
l0 = r1;

int32_t r2 = l0;
int32_t r3 = l0;
int32_t r4 = r3 + 1;
```

This is acceptable.

Modern C compilers are extremely good at removing unnecessary temporaries.

The current optimization strategy is therefore:

> Step 1: generate correct code.
> Step 2: let Clang cook.

More sophisticated optimization can come later.

# Compiler Architecture

The RKotlin compiler is currently written in Kotlin.

Its structure follows a conventional multi-stage design.

Roughly:

```text
source/
    SourceFile
    SourceSpan

lexer/
    Token
    TokenType
    Lexer

ast/
    declarations
    statements
    expressions

parser/
    Parser

semantic/
    types
    symbols
    scopes
    semantic analysis
    bound nodes

ir/
    IR values
    IR instructions
    functions
    modules

backend/
    C backend
```

Each stage has a specific responsibility.

The lexer does not type-check.

The parser does not decide whether a `val` may be reassigned.

The semantic analyzer does not emit C syntax.

The C backend does not resolve names.

This separation matters.

Otherwise the compiler eventually becomes one 8,000-line file named:

```text
Compiler.kt
```

and nobody deserves that.

---

# Error Handling

RKotlin attempts to report errors at the stage where they belong.

For example:

```kotlin
val x: Int32 = 10

x = 20
```

is valid syntax.

The parser should accept it.

Semantic analysis should reject it because `x` is immutable.

Likewise:

```kotlin
var x: Int32 = 10

x = somethingCompletelyWrong
```

may parse correctly but fail during name resolution.

This distinction is intentional.

A syntactically valid program is not necessarily a semantically valid program.

Compilers become much easier to reason about once those ideas are kept separate.

# Roadmap

The roadmap is intentionally approximate.

Compiler roadmaps have a remarkable tendency to become historical fiction.

## Near term

* improve primitive types,
* improve comparison operators,
* improve control flow,
* expand input/output,
* improve object semantics,
* improve member access,
* improve constructors,
* improve scoping,
* improve diagnostics,
* improve generated C,
* add stronger semantic validation,
* improve compiler tests,
* and stabilize more of the grammar.

## Type system

Planned or possible types include:

```text
Int8
Int16
Int32
Int64

UInt8
UInt16
UInt32
UInt64

Float32
Float64

Bool
Char
String
```

Potential future additions:

* arrays,
* nullable types,
* function types,
* user-defined value types,
* pointers,
* generics,
* explicit casts.

The exact design is not finalized.

Anything listed here may eventually be murdered by a better idea.

## Object model

Possible future work includes:

* fields,
* methods,
* constructors,
* visibility,
* interfaces,
* inheritance or a restricted alternative,
* static members,
* value-like objects,
* explicit layout.

RKotlin is object-oriented.

That does not mean every object-oriented feature ever invented must be invited.

Multiple inheritance may remain outside until it produces a sufficiently convincing legal defense.

## Low-Level Features

Long-term low-level functionality may include:

* pointers,
* pointer arithmetic,
* explicit casts,
* raw allocation,
* manual deallocation,
* `unsafe`,
* explicit structure layout,
* alignment controls,
* volatile access,
* FFI,
* C ABI support,
* calling conventions,
* inline assembly,
* architecture-specific intrinsics.

This is where RKotlin stops politely pretending memory is abstract.

## Backends

Possible future backends include:

```text
C
LLVM IR
x86-64
AArch64
WebAssembly
```

A direct native backend would be interesting.

It would also require willingly implementing register allocation.

Future me can deal with that betrayal.

## Self-hosting

A major long-term milestone is rewriting the RKotlin compiler in RKotlin itself.

The bootstrap chain would look roughly like:

```text
Kotlin implementation
        │
        ▼
RKotlin compiler v1
        │
        ▼
RKotlin compiler written in RKotlin
        │
        ▼
RKotlin compiles itself
```

At that point, Kotlin can finally be thanked for its service and gently removed from the bootstrap chain.

Not because Kotlin is bad.

Because the child must eventually leave home.

# Why is the compiler written in Kotlin?

Because Kotlin is pleasant to write.

This creates an obvious philosophical problem.

RKotlin exists partly because I dislike certain parts of Kotlin.

The RKotlin compiler is written in Kotlin.

Therefore the current architecture can be summarized as:

```text
"I don't like Kotlin."

        ↓

writes several thousand lines of Kotlin

        ↓

creates RKotlin
```

This is not hypocrisy.

This is bootstrapping.

Probably.

Kotlin is an excellent language for rapidly developing the first implementation of RKotlin.

Once RKotlin becomes expressive and stable enough, self-hosting becomes possible.

Until then, Kotlin is the ladder.

RKotlin is merely planning to kick it away eventually.

---

# Design Priorities

When design goals conflict, RKotlin generally prefers:

```text
predictability over magic

explicitness over hidden behavior

clear semantics over clever syntax

correct code generation over pretty C

simple compiler architecture over premature abstraction

useful low-level access over artificial purity
```

This does not mean RKotlin should be unnecessarily verbose.

Explicit does not have to mean miserable.

The challenge is finding the point where the compiler helps the programmer without quietly becoming their co-author.

# Is this serious?

Unfortunately, yes.

The jokes are not evidence that the compiler does not exist.

It compiles programs.

It generates C.

The C compiles.

The resulting executable runs.

This is how these things get out of hand.
